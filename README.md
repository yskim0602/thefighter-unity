# TheFighter (더 파이터) — Unity

성장형 복싱 게임 「더 파이터」. **Unity 프로젝트 (독립 저장소)**

**목표 플랫폼: 모바일(App Store / Play Store).** 기본 입력은 터치, 기본 시점은
링사이드를 천천히 도는 브로드캐스트 카메라입니다. 키보드·1인칭은 PC에서
빠르게 테스트하기 위한 보조 경로로 남겨뒀습니다.

이전에 Godot로 만든 프로토타입([yskim0602/thefighter](https://github.com/yskim0602/thefighter))은
기획과 전투 시스템을 검증하는 용도였고, 이 저장소와는 **완전히 별개**입니다.
코드를 기계적으로 변환한 게 아니라, 거기서 확정된 기획을 Unity에 맞는 구조로
다시 설계했습니다 (2절 참고).

## 1. 확정된 기획

**장르**

- MMA가 아닌 **복싱**. 발차기·그래플링 없음
- 전투만큼이나 **성장(커리어)**이 축: 파이트머니로 능력치를 올리고 무대를 올라감
- 지금은 그래픽 품질이 아니라 **실제 복싱 플레이와 타격감**이 우선.
  캐릭터는 캡슐/구 프리미티브 그대로, 실제 모델은 재미가 확인된 뒤에
- **1인칭 복싱을 우선 테스트**

**전투**

| 요소 | 내용 |
| --- | --- |
| 펀치 | 잽 / 스트레이트 / 훅 / 어퍼컷 — 데미지·스태미나·선딜·사거리·가드 관통이 전부 다름 |
| 손 | 양손 글러브. 잽·훅은 앞손, 스트레이트·어퍼컷은 뒷손 |
| 스탠스 | 오소독스 / 사우스포. 앞손·뒷손과 좌우 위치·궤적이 전부 거울상으로 반전 |
| 가드 | 데미지 대폭 감소 + **가드 게이지**. 0이 되면 강제 가드 브레이크(1.5초) |
| 회피 | 짧은 슬립. 스태미나 소모, 쿨다운 있음, 완전 무적은 아님 |
| 스태미나 | 체력과 별개 자원. 연타할수록 소모 증가, 바닥나면 데미지↓ 쿨다운↑ |
| 피격 부위 | 머리(확률적 경직) / 몸통(스태미나 추가 감소) |
| 카운터 | ① 퍼펙트 블록·회피 직후 ② 상대 펀치 선딜(무방비) 처벌 — 두 경로 |
| 다운/KO | 3-다운제. 다운 시 카운트, 펀치 버튼 연타로 빨리 일어남, 3번째 다운은 KO |
| 스타일 | 아웃복서 / 인파이터 / 슬러거 / 복서-펀처 / 카운터펀처 / 프레셔 파이터 6종 |

**스타일 규칙** — 능력치 위에 곱연산으로 얹힘. CPU는 경기 중 상황에 따라
실시간 전환(초반 아웃복서 → 체력 위험 시 인파이터 → 피격 직후 카운터펀처).
플레이어는 스타일을 고르지 않고, 훈련한 능력치 분포에서 자동으로 추론됨.

**커리어 구조** (아직 미구현, 기획은 확정)

홈 → FIGHT → **경기 제의** → 수락/거절 → 경기 → 결과 → 커리어 반영.
상대와 무대를 직접 고르지 않고 게임이 제의를 보냄. 스테이지 1~6은 승수 기반
(10경기 7승 → 승급전), 7~10은 랭크 기반(30 → 1 → 타이틀전 → 방어전).

## 2. Godot 버전과 다르게 설계한 부분

| # | Godot 버전 | Unity 버전 | 왜 |
| --- | --- | --- | --- |
| 1 | `Fighter.gd` 베이스 클래스를 `PlayerController`/`AIController`가 **상속** | `Fighter` + `IFighterBrain`(`PlayerBrain` / `AIBrain`) **컴포지션** | 상속은 "누가 조종하는가"를 타입에 박아버림. 브레인을 분리하면 같은 파이터에 AI를 붙여 AI vs AI 밸런스 테스트, 리플레이, 스파링 모드가 전부 공짜로 열림 |
| 2 | 머리/몸통을 **펀치별 확률**로 굴림 | 실제 **히트박스 2개**(머리 구 / 몸통 캡슐)에 글러브를 오버랩 | 1인칭이 주력이면 "내가 조준한 곳에 맞는다"가 핵심. 마우스를 내리면 보디, 올리면 헤드 — 확률이 아니라 플레이어의 선택이 됨 |
| 3 | 거리 기반 히트 판정 | 글러브 트랜스폼 위치로 판정 | 보이는 글러브가 곧 히트박스. 모션과 판정이 어긋나지 않음 |
| 4 | `.tscn` 씬 파일에 노드 배치 | `BoxingBootstrap`이 **코드로 씬을 구성** | 씬 파일은 diff도 리뷰도 머지도 안 됨. 프로토타입 단계에선 코드가 훨씬 빠름 (에디터 메뉴로 씬 생성 지원) |
| 5 | 글러브가 1인칭에서 화면을 다 가림 | 1인칭 **전용 포즈 세트** + 축소 스케일 | 4절 참고 |
| 6 | 스타일 전환이 최대 체력에도 영향 | `SetBaseStyle`(풀 결정) / `SetActiveStyle`(전술 전환) 분리 | AI가 인파이터로 바꿀 때 최대 체력이 같이 흔들리면 안 됨 |
| 7 | `CareerConfig.gd`에 수치 집중 | `CombatTuning.cs` + `BoxingStyles.cs`에 집중 | 이 방식은 좋았으니 유지. 밸런스는 이 두 파일만 건드림 |

## 3. 실행 방법

1. 이 저장소를 클론 (또는 ZIP을 원하는 위치에 압축 해제)
2. Unity Hub → **Installs** 탭에서 에디터가 없으면 설치 (Unity 6000.0 LTS 권장,
   2021.3 이상이면 다른 버전으로 열어도 됩니다)
3. Unity Hub → **Projects** → 오른쪽 위 **Add** → *Add project from disk* →
   **클론한 폴더 자체**를 선택 (`Assets` 폴더가 보이는 그 위치)
4. 프로젝트를 열기 — 처음 열 때 `Library/`, `Packages/`, 나머지
   `ProjectSettings/`를 Unity가 기본값으로 생성하므로 몇 분 걸립니다
5. 상단 메뉴 **The Fighter → Create Boxing Prototype Scene**
6. **Play** ▶

씬을 만들지 않고 직접 해도 됩니다: 빈 씬에 빈 GameObject 하나 만들고
`BoxingBootstrap` 컴포넌트만 붙이면 나머지(링·조명·양 선수·카메라·HUD)는
전부 실행 시점에 자동 생성됩니다.

> 만약 `Input.GetKey` 관련 에러가 나면 Project Settings → Player →
> **Active Input Handling**을 `Input Manager (Old)` 또는 `Both`로 바꿔주세요.
> 이 프로토타입은 의도적으로 구버전 입력을 씁니다(패키지 의존성 0).

## 조작법 — 터치 (모바일, 기본)

가로 화면 기준. 양쪽 엄지가 닿는 자리만 쓰도록 배치해서, 어느 쪽도 손을
뻗을 필요가 없습니다.

| 조작 | 동작 |
| --- | --- |
| **왼쪽 영역 드래그** | 플로팅 스틱. 처음 닿은 지점이 중심. 전진/후진/서클링 — **항상 상대 기준** |
| **오른쪽 영역 탭** | 왼쪽 절반 = 잽(앞손), 오른쪽 절반 = 스트레이트(뒷손) |
| ↑ **탭 위치가 높으면 헤드 / 낮으면 보디** | 마우스 조준을 터치로 옮긴 것. **탭한 곳으로 펀치가 갑니다** |
| **위로 스와이프** | 어퍼컷 |
| **좌우로 스와이프** | 훅 |
| **아래로 스와이프** | 회피(슬립) |
| **길게 누르기** | 가드 (떼면 바로 내려가고, 펀치를 내면 자동 해제) |
| 다운 중 탭 | 마샤 — 일어나는 시간 단축 |

스와이프 거리는 `Screen.dpi` 기준 인치로 계산하므로 기기가 바뀌어도 같은
손동작입니다. 영역·임계값은 `TouchBrain` 인스펙터에서 실행 중 조정 가능합니다.

**에디터에서 터치 테스트**: `BoxingBootstrap` → `Controls`를 `Touch`로 바꾸면
마우스가 손가락 하나를 대신합니다(손가락이 하나뿐이라 이동과 펀치 동시 입력은
안 됩니다 — 제스처 인식 확인용). 화면에 영역·분할선·스틱이 오버레이로 표시됩니다.

## 4. 1인칭 글러브 — 화면을 가리던 문제

> 1인칭은 이제 기본 시점이 아닙니다(5절의 브로드캐스트 카메라가 기본). 이 절의
> 해법은 PC 1인칭에서 유효한 것이고, **폰에서는 바로 이 위치가 엄지 밑에 깔립니다.**
> 1.5단계 실기기 검증에서 1인칭을 유지할지 결정해야 합니다.

Godot에서 1인칭으로 플레이했을 때 글러브가 화면의 너무 많은 부분을 차지해서
상대가 안 보이는 문제가 있었습니다. 원인은 **3인칭용 글러브 위치를 1인칭에서
그대로 썼기 때문**입니다. 눈높이 카메라에서 팔 길이만큼 떨어진 구는 화면
높이의 절반을 그냥 먹습니다.

이 버전은 `GloveRig`가 **시점별로 다른 rest 포즈 세트**를 씁니다:

| | 평소(idle) | 가드 |
| --- | --- | --- |
| 화면상 위치 | 화면 **아래쪽 가장자리**에 살짝 걸침 | 중앙선 근처까지 올라와 시야를 감쌈 |
| 가운데 시야 | 완전히 비어 있음 | 두 글러브 사이에 틈이 남음 (피카부 가드) |

추가로 1인칭일 때는 글러브 스케일 자체를 **0.62배**로 줄입니다.

```
FirstPersonIdleLead   (0.20, 1.41, 0.50)   // 눈(y=1.62) 기준 22cm 아래
FirstPersonIdleRear   (0.27, 1.38, 0.44)
FirstPersonGuardLead  (0.14, 1.56, 0.42)   // 눈 기준 6cm 아래까지 올라옴
FirstPersonGuardRear  (0.18, 1.52, 0.38)
FirstPersonGloveScale 0.62
```

**중요**: 이 포즈는 *평소 자세*에만 적용됩니다. 펀치를 뻗는 동안 글러브는
실제 궤적(어깨 → 조준점)으로 수렴하기 때문에, **1인칭과 3인칭의 펀치가
닿는 위치는 완전히 동일**합니다. 보기 좋게 낮췄다고 펀치가 짧아지지 않습니다.

튜닝은 실행 중에 바로 할 수 있습니다 — Hierarchy에서 플레이어 오브젝트 →
`Glove Rig` 컴포넌트의 값을 Play 모드에서 바꾸면 즉시 반영됩니다.
마음에 드는 값을 찾은 뒤 `GloveRig.cs`의 기본값에 옮겨 적으면 됩니다.

## 5. 카메라 — 플레이용은 각도를 지킵니다

**떠도는 카메라는 TV처럼 보이고, 바닥이 기울어진 것처럼 플레이됩니다.**

풋워크가 상대 기준이라 "왼쪽으로 서클링"은 선수 자기 좌표에서 항상 왼쪽입니다. 그런데
카메라가 마지막으로 누른 때로부터 22° 돌아가 있으면, **같은 키가 화면에서 다른 곳을
가리킵니다.** 호가 22° 범위를 훑고 있었으니 근육 기억이 형성될 수 없습니다.

이건 촬영 기법 문제가 아니라 **조작 문제**입니다. 그래서 기본값을 바꿨습니다:

| `Shot` | |
| --- | --- |
| **`Stable`** (기본) | 한 각도(27°)를 유지, **±2.5°** 만 ~6초 주기로 숨 쉼 |
| `Roaming` | 예전의 떠도는 링사이드 카메라 — 보기 좋고 플레이하기 나쁨. 리플레이·하이라이트용 |

27°는 뒤통수가 시선을 막지 않는 최소각(22°)보다 여유가 있는 값입니다.

### 예전 브로드캐스트 호 (Roaming)

기본 시점은 고정 카메라가 아니라, 링사이드에서 **천천히 호를 그리며 움직이는
중계 카메라**입니다 (Tactic Boxing / Boxing Simulator 계열의 연출).

- **궤도 드리프트**: 플레이어 등 뒤에서 **22°~44°** 범위 안에서 목표 각도를 랜덤하게
  잡고 천천히 이동합니다. 도착하면 잠시 머물다 다음 각도로 — 카메라맨이 자리를
  옮기는 리듬입니다
- **거리 호흡**: 두 선수가 붙으면 당겨지고(2.45m), 벌어지면 물러납니다(3.95m)
- **푸시인**: 다운·카운터·클린히트에서 순간적으로 파고듭니다 (`PushIn()`)
- **다운 추적**: 누군가 쓰러지면 시선이 그쪽으로 기울어집니다

**`OrbitMin`(22°)이 중요한 이유**: 각도가 작으면 카메라·플레이어·상대가 거의 일직선이
되어서, **상대 얼굴을 보는 시선이 내 캐릭터 뒤통수를 그대로 관통합니다.** 높이를
올리는 것만으로는 해결되지 않습니다 (정수리를 내려다볼 만큼 올라가야 함). 옆으로
한 걸음 비키면 어떤 높이에서든 해결되므로, 호가 **중앙을 아예 지나가지 않게** 했습니다.

| 궤도 각 | 시선이 내 몸을 지나는 거리 | |
| --- | --- | --- |
| 0° | 0.00m | 완전히 가림 |
| 16° | 0.23m | 머리를 스침 |
| **22°** | **0.31m** | 비켜감 |
| 44° | 0.58m | 넉넉함 |

**한쪽 사이드에만 머무는 이유**: 풋워크가 카메라가 아니라 **상대 기준**이기 때문입니다.
카메라가 상대 뒤까지 돌아가면 플레이어의 "왼쪽으로 서클링"이 화면에서는 오른쪽으로
보여서 조작이 뒤집힙니다. 사이드는 경기 시작 시 한 번 정해지고 끝까지 유지됩니다 —
실제 링사이드 카메라가 하는 방식이기도 합니다.

- `Height` 2.2m / `Look Height` 1.45m — 약간 내려다보는 중계 앵글
- `Opponent Bias` 0.5 — 시선을 상대 쪽으로 당겨서 상대를 화면 중앙에 둡니다. 읽어야
  하는 펀치가 거기서 나오니까, 내 캐릭터는 프레임 가장자리로 밀어도 됩니다

1인칭은 `V`로 전환되고, 터치 환경에서는 조준을 `TouchBrain`이 담당하므로
카메라에 의존하지 않습니다.

## 6. 스탯 밸런스

네 가지 스탯이 각각 **눈에 보이는 하나**를 담당합니다. 수치표를 안 봐도 상대가
어떤 선수인지 싸우는 중에 읽히는 게 목표입니다.

| 스탯 | 담당 | 공식 |
| --- | --- | --- |
| **파워** | 펀치 데미지 | `5 + Power × 0.85` |
| **체력(Endurance)** | 체력 풀 + 스태미나 풀 | `70 + End × 5.5` / `60 + End × 2.5 + Skill × 1.5` |
| **스피드** | 풋워크 + **펀치가 나가는 속도**(선딜·타격) | `1.8 + Spd × 0.075` / `1 / (0.80 + Spd × 0.020)` |
| **스킬** | **펀치 회수 속도**(후딜) + 리치 | `1 / (0.85 + Skill × 0.015)` / `0.70 + Skill × 0.0025` |

스피드와 스킬을 나눈 게 핵심입니다. **스피드는 주먹이 빨리 나가고, 스킬은 빨리
돌아옵니다** — 그래서 스킬이 높은 선수는 단순히 빠른 게 아니라 "빈틈을 안 주는"
선수가 됩니다 (빈틈 카운터가 바로 후딜을 노리는 판정이라 체감이 직접적입니다).

**체력바는 정규화하지 않습니다.** 공용 기준값(`CombatTuning.HealthBarReference`)에
대고 그리기 때문에, 체력 스탯이 높은 선수는 **바 자체가 더 깁니다**. 바의 *길이*는
풀, *채워진 양*은 남은 체력입니다. 뒤에 희미한 전체 트랙이 같이 그려져서 두 선수를
바로 비교할 수 있고, HP 숫자도 함께 표시됩니다.

스타일 배율(`BoxingStyles`)은 이 위에 곱연산으로 얹히고, **최대 체력·스태미나는
입장할 때의 스타일(`SetBaseStyle`)만 결정**합니다 — AI가 경기 중 인파이터로
바꿔도 바가 흔들리지 않습니다.

## 7. 경기 규칙 — 라운드와 판정

복싱의 **구조**는 그대로 가져왔습니다. 공, 라운드별 페이스 배분, 코너, 내가
지고 있을 수 있는 채점표 — 이게 "경기를 뛴다"는 느낌의 전부입니다.
**시간만 압축**했습니다. 실제 12라운드 타이틀전은 47분이고, 그걸로는 커리어를
돌릴 수 없습니다.

| | 값 | 이유 |
| --- | --- | --- |
| 라운드 길이 | **90초** | 실제의 절반. 페이스·가스 배분이 실제 판단이 되고 공이 반가울 만큼은 길지만, 한 라운드가 늘어지지는 않는 길이 |
| 라운드 휴식 | **12초** | 실제 1분에서 압축. 채점표 읽고 숨 돌릴 만큼. 나중에 코너 연출·세리머니가 들어갈 자리 |
| 경기 전 | 2.5초 | 개시 공 (추후 입장 연출 자리) |

**경기 거리는 커리어 단계에 따라 늘어납니다** (`RoundRules.RoundsForStage`).
복싱이 실제로 그렇고, "진짜 선수가 되는 느낌"도 거기서 나옵니다 — 데뷔전은
지치기도 전에 끝나고, 타이틀전은 버텨내야 하는 시련입니다.

| 커리어 단계 | 라운드 | 총 길이(휴식 포함) |
| --- | --- | --- |
| 1~2 (언더그라운드·아마추어) | 3 | 약 4.9분 |
| 3~4 (루키·파이트리그) | 4 | 약 6.6분 |
| 5~6 (엘리트·월드시리즈) | 5 | 약 8.3분 |
| 7~8 (랭크·TOP 10) | 6 | 약 10분 |
| 9~10 (타이틀샷·챔피언십) | 8 | 약 13.4분 |

### 채점 — 10점 머스트, 심판 3명

`Scorecard.cs`. 라운드마다 세 심판이 **독립적으로** 채점합니다.

- 각 심판은 **클린 펀치 / 유효타 수 / 방어(블록·슬립) / 다운**에 대한 가중치가
  서로 다르고, 매 경기 새로 뽑힙니다. 여기에 약간의 노이즈가 붙습니다
- 이긴 쪽 10점, 진 쪽 9점. 격차가 거의 없으면 **10-10**
- **다운당 1점 차감** → 10-8, 두 번이면 10-7
- 판정: **만장일치 / 스플릿 / 다수 / 무승부**

가중치가 심판마다 다른 게 핵심입니다. 같은 경기가 카드마다 다르게 적히고,
접전 라운드가 실제로 흔들리고, **스플릿 판정**이 나옵니다 — 마지막 라운드를
남기고 카드상 2라운드 뒤져 있다는 감각이 이 시스템이 존재하는 이유입니다.

### 코너 회복과 3-다운제

- 복싱에선 회복이 없지만, 아무것도 안 돌려주면 매 경기 TKO로 끝나고 채점표가
  무의미해집니다. 그래서 **코너가 조금 돌려줍니다** — 스태미나는 많이,
  체력은 조금
- **경기가 깊어질수록 코너 효과가 줄어듭니다**(`RestHealthFade`).
  그래서 후반 라운드가 무섭습니다
- 아무리 두들겨 맞았어도 최소 22%는 들고 다음 라운드에 나갑니다. 공에 살아난
  선수가 다음 라운드 첫 잽에 또 다운되는 걸 막는 장치입니다
- **3-다운제는 같은 라운드 기준**입니다(실제 규칙대로). 라운드가 바뀌면
  카운트가 초기화되고, 경기 전체의 다운은 **점수로** 남습니다
- 라운드 종료 공이 울리면 카운트가 멈춥니다 — "공에 살았다". 단 그 다운은
  채점표에 그대로 남습니다

## 8. 타격감 — 어디서 나오고 어떻게 만지는지

타격감은 한 가지가 아니라 **여러 층이 동시에 터지는 것**입니다. 지금 들어간 층:

| 층 | 무슨 일이 | 어디 |
| --- | --- | --- |
| **피격 반응** | 맞은 쪽 몸이 실제로 움직임. 머리샷은 머리가 뒤·옆으로 꺾이고, 보디샷은 몸이 접힘 | `FighterRig.PlayHitReaction` |
| **글러브 정지** | 명중 순간 스트라이크를 끊고 바로 후딜로 — 주먹이 상대를 통과하지 않음 | `Fighter.AdvancePunch` |
| **몸의 커밋** | 펀치마다 상체가 감겼다 풀리고 어깨가 돌아가며 앞으로 밀고 나감 | `FighterRig.UpdateBody` |
| **히트스톱** | 접촉 순간 `Time.timeScale`을 떨어뜨림 (클린 65ms / 블록 28ms / 다운 180ms) | `ImpactFeedback.Freeze` |
| **카메라** | 흔들림 + FOV 킥 + 브로드캐스트 푸시인. **때릴 때도** 작게 킥이 들어감 | `FightCamera` |
| **화면 플래시** | 내가 맞으면 화면 전체가 붉게 물듦 — 3인칭에선 이게 없으면 맞은 걸 못 느낌 | `FightHud.DrawDamageFlash` |
| **소리** | 절차 생성 타격음. **펀치 무게에 따라 피치가 달라짐** (잽은 높고 어퍼컷은 낮음) | `ImpactFeedback.PlayPunch` |
| **넉백** | 관통 데미지만큼 밀림 (이전보다 약 2배로 올림) | `CombatTuning.KnockbackPerDamage` |
| **다운 포즈** | 무릎을 꿇듯 몸이 주저앉음. 이전엔 다운돼도 그냥 서 있었음 | `FighterRig.DownPosition/DownRotation` |

### 전신 연동 — 프로젝트 최우선 품질 기준

> 상세 규칙은 저장소 루트 **`CLAUDE.md`** 에 있습니다. 애니메이션·자세·전투 코드를
> 건드릴 때마다 먼저 읽습니다.

복싱은 **발 → 무릎 → 골반 → 허리 → 어깨 → 팔 → 주먹**이 연결된 전신 운동입니다.
금지사항을 "조심해서" 지키는 게 아니라 **구조가 어기지 못하게** 만들었습니다.

| 보장 | 어떻게 |
| --- | --- |
| 공격이 자세를 덮어쓸 수 없다 | 베이스 레이어가 **항상** 재생됩니다. 끄는 코드가 없습니다 |
| 공격 종료 시 현재 상태로 복귀 | 상체 가중치만 빠집니다. 아래는 계속 돌고 있었으니 "복귀"할 게 없습니다 |
| 앉은 자세 유지 | `CrouchPose` 가 클립과 **무관하게** `CrouchAmount` 를 읽어 무릎을 접습니다 |
| 골반·척추가 펀치에 연결 | 상체 마스크에서 `Body`(Hips/Spine/Chest)를 **켠 채로** 둡니다 |
| 체중 이동이 있다 | 펀치 커밋이 모델 유무와 **무관하게** 항상 적용됩니다 |

#### 찾은 버그: 체중 이동이 0으로 곱해지고 있었습니다

`PunchLunge`, `PunchTorsoYaw`, `PunchLean`, `WeightShiftDegrees` 가 전부
`ProceduralMotionWeight` 로 곱해지고 있었고, **Bootstrap 은 모델이 있으면 그 값을
0으로 설정**합니다. 즉 모델을 넣은 순간부터 **모든 펀치에 체중 이동이 완전히
없었습니다.** "팔만 움직이고 몸의 체중 이동이 없음"이 정확히 이것이었고, 원인은
곱셈 하나였습니다.

이제 다이얼이 둘로 갈렸습니다:

- `ProceduralMotionWeight` — 숨쉬기·스텝 바운스 등 **클립이 이미 하는 것**. 모델
  있으면 0
- **`WeightTransferWeight`** — 펀치 커밋 + 서클링 롤. **항상 1.** 클립은 펀치의
  *모양*은 줄 수 있지만 *구동*은 못 줍니다 — 주먹이 언제 도착해야 하는지는 코드만
  알기 때문입니다

#### 어깨도 체인에 들어갔습니다

`ArmPose` 가 팔 IK 전에 어깨를 목표 쪽으로 일부 돌립니다 (`Shoulder Drive` 0.35).
없으면 리치가 전부 팔꿈치 펴기에서 나오는데, 팔꿈치에서 뻗는 펀치는 몸통이 아무리
돌아도 "팔만" 보입니다.

#### 전신이 필요한 펀치는 opt-in

`ClipVariant.FullBody` 로 특정 클립만 전신 레이어로 보낼 수 있습니다. **대가는
앉은 자세입니다** — 전신 펀치는 다리를 덮어쓰므로 낮은 자세에서 던지면 일어섭니다.
뒷발 드라이브가 펀치의 본질인 클립(깊은 어퍼컷)에만, 그리고 앉아서 던져본 뒤에만
쓰세요.

### `PostureProbe` — 10개 테스트를 수치로

**Play 중에 `P`** 를 누르면 Game 뷰 **오른쪽 아래**에 패널이 뜹니다. `F1` 로 최악값
리셋 (O는 어퍼컷이라 안 씁니다). 처음 켜면 "learning the stance" 가 잠깐 뜨는데,
**가만히 똑바로 서 있으면** 기준선을 잡고 수치가 나옵니다.

인스펙터에서 `BoxingBootstrap` → **Posture Probe On** 을 켜면 처음부터 보입니다.

보고하는 것:

| 표시 | 측정하는 실패 |
| --- | --- |
| `hips` | 공격할 때 갑자기 일어남 / 높이가 튐 |
| `feet` | 발이 뜸 / 지면에 박힘 / 공중에서 펀치 |
| `snap` | 몸이 순간적으로 원점으로 돌아감 |
| `twist` | 골반과 상체가 따로 움직임 |
| `drive` | **팔만 움직이고 체중 이동 없음** |
| `crouch` | 자세가 덮어써짐 / 종료 후 Standing 강제 복귀 |

기준선(스탠스 엉덩이 높이, 발목 높이)은 **가만히 서 있을 때 학습**합니다 — 모델과
아이들 클립마다 다르니 하드코딩할 수 없습니다. 그리고 **리셋 이후 최악값을 계속
들고 있습니다**: 나쁜 프레임은 보통 펀치 중간의 한 프레임이고, 보려고 하면 이미
지나가 있습니다.

테스트 1~10을 한 번 돌리고 `drive` / `crouch` / `hips` 세 줄만 붙여주시면 어디가
문제인지 바로 짚을 수 있습니다.

### 모션을 좋게 만드는 3가지 방법 — Mixamo만이 아닙니다

"Mixamo에서 받는 것 말고 방법이 없나?"에 대한 답입니다. **지금 병목은 Mixamo가
아닙니다.** 클립을 쓰는 방식이 병목이었습니다.

#### 1. 임포트 설정 (`.fbx.meta` — 텍스트라서 제가 편집 가능)

`clipAnimations`, 루프, 미러, 트림, Root Transform. 다만 **지금은 거의 의미가
없습니다** — 타이밍을 코드가 쥐고 있어서 클립의 Loop Time도 길이도 읽지 않고,
Root Transform Y 문제는 `HipHeightLock`이 이미 처리합니다. 과대평가하지 마세요.

#### 2. 런타임 파라미터 (`Window` / `Speed`)

클립의 어느 구간을 쓸지, 어떤 속도로. 이미 들어가 있습니다.

#### 3. 코드로 포즈를 덧씌우기 ← **여기가 전부입니다**

클립을 "그대로 재생하는 것"이 아니라 **베이스로 쓰고 위에 얹는** 겁니다. 격투
게임이 타격감을 만드는 방식이 이거고, 새 클립이 하나도 필요 없습니다.

### 레이어 3개 — 마네킹과 복서의 차이

**이게 "굉장히 구린" 가장 큰 원인이었습니다.** 믹서가 하나뿐이어서 펀치 클립이
**온몸을 덮었습니다.** 즉 펀치할 때마다 다리가 걷던 중간에 얼어붙고, 몸은
계속 움직이니까 **멈춘 발로 캔버스를 미끄러져 다녔습니다.**

복서의 발은 멈추지 않습니다. 스텝을 밟으면서 잽을 내고, 잽은 *여전히 진행 중인*
풋워크 위에 얹힌 팔과 상체입니다. 클립을 아무리 좋은 걸로 바꿔도 이건 안 고쳐집니다 —
문제는 다리에게 멈추라고 말하고 있다는 것이니까요.

```
layer 0   스탠스 + 풋워크   온몸, 항상 재생
layer 1   펀치 + 슬립       상체 마스크 — 아래에서 다리는 계속 움직입니다
layer 2   다운              온몸, 전부 덮어씀
```

마스크는 **코드로 만듭니다** (`AvatarMask`). 에디터에서 `.mask` 에셋을 만들
필요가 없습니다. 상체 레이어에서 끈 것: `Root`, `LeftLeg`, `RightLeg`, 발 IK.

상체는 **몸통(Body)을 포함**합니다 — 펀치에 허리 회전이 실려야 무게가 보이니까요.
대가로 펀치 클립이 엉덩이 *높이*까지 건드리는데, 그걸 `HipHeightLock`이 상쇄합니다.
(`Punch Drives Torso` 를 끄면 몸통도 베이스에 맡기지만, 펀치가 팔만 휘두르는
것처럼 보입니다.)

### 발 미끄러짐 — 스텝은 이동한 거리를 따라갑니다

풋워크 클립이 **고정 속도로** 돌고 있었습니다. 다른 속도로 움직이는 몸 아래에서
보행 사이클이 자기 타이머로 도는 게 정확히 "아이스 스케이팅"으로 보이는 원인이고,
어떤 클립도 여기서 자유롭지 않습니다.

이제 `_strideRate` 가 실제 이동 속도를 따릅니다 (`Stride Rate Idle` 0.55 →
`Stride Rate Full` 1.35). 정지 상태에서도 0이 아닙니다 — 완전히 멈춘 발은 고장난
것처럼 보이고, 복서는 항상 체중을 옮기고 있습니다.

### 손은 집에 돌아옵니다 — 그리고 한 손만 나갑니다

Mixamo의 섀도복싱 클립은 손을 **낮고 느슨하게** 내려놓습니다. 그래서 펀치 사이에
턱을 내놓고 서 있게 되는데, 클립이 원인이니 클립으로는 안 고쳐집니다.

`GuardPose` 에 두 가지가 들어갔습니다:

- **`Idle Guard Weight`** (0.45) — 가드 버튼을 안 눌러도 손이 광대뼈 쪽으로
  당겨집니다. 공짜인데 "맞을 줄 아는 사람"처럼 보입니다
- **던지는 팔만 풀립니다.** 왼손으로 치면 왼팔만 자유로워지고 **오른손은 집에
  남습니다.** 두 손을 다 내리고 치는 복서는 맞는 복서입니다 — 이 디테일 하나가
  복서와 그냥 휘두르는 사람을 가릅니다

놓아주는 건 빠르고(`Release Speed` 40) 돌아오는 건 느립니다(`Blend Speed` 9) —
펀치가 자기 가드 페이드를 기다리면 엉뚱한 데서 시작합니다.

### Mixamo가 정말 못 주는 것

| | 대안 |
| --- | --- |
| 체중이 실린 진짜 펀치 (Mixamo 복싱은 대부분 섀도복싱) | 위 코드 레이어로 상당 부분 보완. 더 필요하면 유료 모션 라이브러리 (Kubold `Boxing Animset`, ActorCore) |
| 피격 반응, 다운, 일어나기 | Mixamo에 `taking punch` / `knocked out` 있습니다 |
| 어퍼컷 | Mixamo에 있습니다 |
| 클린치, 코너, 입장 | 유료 또는 직접 키프레임 (Blender) |

### 캐릭터가 떠오르던 이유 — 제가 넣은 양의 피드백 루프

클립별 엉덩이 높이 학습에 **측정에 없는 보정을 더하고** 있었습니다:

```csharp
float raw = hipHeight + _baseOffset * FootworkHipLock;   // 틀림
```

`hipHeight` 는 이미 **보정 전** 값입니다 — Animator가 LateUpdate 전에 모든 본을 그래프
에서 다시 포즈하므로, 지난 프레임에 엉덩이에 쓴 값은 이미 사라져 있습니다. 거기에 현재
오프셋을 다시 더하니 **학습된 기준이 오프셋만큼 부풀고 → 다음 오프셋이 부풀고 → 다음
기준이 부풀고**, 발산했습니다.

시뮬레이션:

| | 한 방향 10초 홀드 후 |
| --- | --- |
| 버그 | 오프셋 **+0.455m** — 몸이 45cm 떠오름 |
| 수정 | 오프셋 +0.040m — 올바른 값 |

**발산이라 오래 누를수록 높아집니다.** "상대보다 더 높이 있게 보인다"가 정확히 이것이고,
한 방향을 계속 누를 때만 나타나는 이유도 그래서입니다.

같이 **상한(`FootworkHipLimit` 0.1m)** 도 걸었습니다. Mixamo 클립은 엉덩이 높이가 몇
센티 차이 날 뿐 30cm씩 다르지 않으니, 그보다 크면 키 큰 클립이 아니라 학습 버그입니다 —
그리고 여기 버그는 링 위에 떠 있는 선수입니다.

### 펀치 클립이 반대 손이면 — 경고로 알려줍니다

**Playables API에는 런타임 미러가 없습니다.** 코드로 고칠 수 없습니다.

손이 어긋나면 **아무것도 에러가 안 납니다** — 클립은 한쪽 팔을 휘두르고, 히트 판정·조준
IK·가드 해제는 반대 팔을 따라갑니다. 결과는 "펀치가 상대 근처에도 안 가는데 이유를 알
수 없음"입니다. 그래서 `clip fit` 로그가 말해줍니다:

```
UPPERCUT  Left Uppercut  WRONG HAND - the fight throws this with the right
          (Rear hand, Orthodox), the clip swings the left.
          Duplicate the clip with Mirror ticked, or change this punch's Hand in PunchLibrary.
```

**왼손 어퍼컷을 받으셨다면 선택이 둘입니다:**

| | |
| --- | --- |
| **클립을 미러링** (권장) | 어퍼컷이 뒷손 파워 펀치로 남습니다. Animation 탭 → Clips 에서 `+` 로 복제 → `Mirror` 체크 → Apply |
| `PunchLibrary` 에서 `Hand = Lead` 로 | 리드 어퍼컷은 실제로 있는 펀치지만, 잽·훅과 같은 손이 되어 **원투 콤보가 불가능**해집니다 (콤보 캔슬은 반대 손만) |

### 어퍼컷이 너무 크던 이유 — 그리고 `Window`로는 못 고칩니다

Mixamo 어퍼컷 테이크는 엉덩이에서 감아 어깨 위로 끝나는 **풍차**입니다. 0.85초짜리
펀치에 자동 맞춤을 하면 그 풍차가 화면에 전부 나옵니다.

**창을 줄이는 건 답이 아닙니다.** 창은 `PunchProgress` 가 펀치 전체에 걸쳐 스크럽하므로,
같은 시간에 프레임이 적어지면 **슬로모션**이 됩니다:

| | 창 | 보이는 양 | 속도 |
| --- | --- | --- | --- |
| 자동 맞춤 | 0.00–0.79 | 0.85초 | 1.00x |
| 창을 절반으로 | 0.00–0.36 | 0.38초 | **0.45x — 슬로모션** |

**지속시간이 진짜 레버입니다.** 다만 처음에 너무 많이 잘랐습니다:

| | 지속시간 |
| --- | --- |
| 원래 | 0.85초 — 풍차 |
| 지난 푸시 | 0.61초 — **너무 짧음** |
| **현재** | **0.73초** |

여기가 그 노브입니다 — 올리면 클립이 더 보이고, 내리면 덜 보입니다. 속도는 항상 1.00x.

`RiseArc` 도 0.45 → 0.3 으로 낮췄습니다 — 수직 궤적이 "너무 크다"의 나머지 절반이었습니다.

> 그래도 스윙이 크면 그건 클립 자체이고, 레버는 `Window` 직접 입력(앞부분만)뿐입니다.
> 다만 위 표대로 느려지는 대가가 따릅니다.

### 빗나간 펀치는 소리가 없습니다

`ImpactFeedback.WhiffVolume` 기본 **0**. 안 닿은 펀치(헛손질·회피당함) 둘 다 무음입니다.
막힌 펀치와 들어간 펀치는 소리가 납니다 — **닿았으니까요.**

모든 헛손질에 바람 소리가 나면 그 소리만 들어서는 **아무 일도 안 일어난 것과 구분이
안 됩니다.** 유일하게 결과와 무관하게 울리는 단서라서, 결국 의미를 잃고 적중을 묻습니다.
빗나감이 조용해야 적중이 사건이 됩니다.

### 가드 게이지가 바닥나면

게이지만으로는 **깨지는 순간까지 가드가 공짜**였습니다 — 비용이 스태미나뿐이고 그건
회복되니까요. 실제로 손을 들고 버티는 선수는 **팔로 매를 받고 있고 그러면서 탱크를
비우고** 있습니다.

| 상태 | 비용 |
| --- | --- |
| 게이지 30% 이하 | 스태미나 소모가 **최대 1.8배**까지 상승 — 바닥나는 게 **느껴집니다** |
| 게이지 소진 + **계속 누름** | **체력 −5/초**, 스태미나 −18.2/초 |
| | 그리고 **손은 올라가지 않습니다** — 버텨서 얻는 게 없습니다 |

체력 136이면 27초를 고집해야 비지만, 그 27초 동안 가드는 전혀 작동하지 않습니다.
게이지는 제안이 아니라 자원입니다.

### 무게중심 — 파워는 팔이 아니라 발에서 나옵니다

복싱의 파워는 **체중을 옮기는 것**입니다. 뒷발에 실린 체중을 앞발로 보내는 게 펀치고,
이미 앞으로 쏟아진 상태에서 던지는 오른손은 **옮길 게 남아 있지 않습니다.**

이게 모델링이 **아예 안 되어 있었습니다** — 발이 뭘 하든 모든 펀치가 똑같이 들어갔습니다.

`Fighter.Weight` (뒷발 −1 ↔ 앞발 +1). 세 가지가 서로 다른 값을 요구할 수 있고,
그게 핵심입니다 — **들어가면서 오른손을 던지는 건 자기 펀치의 파워를 스스로 빼는 것**
입니다.

| 같은 펀치, 다른 발 | 파워 |
| --- | --- |
| 스트레이트 — 스탠스에서 | 74% |
| 스트레이트 — **이미 들어간 상태에서** | **40%** |
| 잽 — 스탠스에서 | 92% |
| 잽 — 이미 들어간 상태에서 | 82% |

리드 핸드는 체중 의존도가 낮습니다 (18%). **잽이 거리 측정용인 이유**가 그겁니다.

체중은 **몸에도 보입니다** — `FighterRig` 가 데미지가 읽는 것과 **같은 숫자**를 읽어서
상체를 기울입니다. 자세와 파워가 어긋날 수 없습니다. `P` 패널의 `weight` 줄에 수치가 나옵니다.

### 타격 거리 — 닿는 것과 제대로 맞추는 건 다릅니다

가슴에 눌려 막힌 스트레이트는 뻗을 공간이 없고, 사거리 한계에서 던진 건 팔만 가고
몸이 뒤에 남습니다. 둘 다 **닿기는 합니다.**

| | 0.62m | 0.70m | 0.80m | 0.90m | 1.00m |
| --- | --- | --- | --- | --- | --- |
| 잽 | 78% | 90% | 93% | 76% | — |
| 스트레이트 | 70% | 82% | **97%** | 88% | 73% |
| 훅 | **94%** | 91% | — | — | — |
| 어퍼컷 | **94%** | 77% | — | — | — |

**짧은 펀치는 안쪽에서, 긴 펀치는 바깥에서 이깁니다.** 펀치별 특수 처리는 없습니다 —
각 펀치의 사거리가 이미 다르니 그 비율에서 자동으로 나옵니다.

> 처음엔 눌림 기준을 거리 0에서 재서 **거의 작동하지 않았습니다** — 선수는 0.62m보다
> 가까이 설 수 없으니 모든 펀치가 점착거리에서 86%를 유지했습니다. 각 펀치 **자기
> 사거리의 비율**로 재니까 비로소 갈립니다.

### 데미지 모델 — 복싱은 체력바로 안 돌아갑니다

> "진짜 복싱에서는 피가 의미가 없고 얼굴 제대로 몇대 맞으면 쓰러진다"

그래서 펀치가 **맞은 부위에 따라 세 가지 다른 일**을 하고, 그중 하나만 체력바입니다.

| | 머리 | 몸통 |
| --- | --- | --- |
| 체력바 | ×1.25 | ×0.8 |
| **턱 (`HeadTrauma`)** | **채웁니다** | — |
| 스태미나 | — | ×1.5 |

**머리 데미지를 체력에 그냥 곱하는 건 안 됩니다.** 해봤는데 ×2.1이면 클린 스트레이트
한 방이 체력의 1/4을 가져가서 **모든 경기가 1라운드에 끝나고 채점이 무의미**해집니다.

#### 턱 — 경기를 끝내는 건 이쪽입니다

`HeadTrauma` 는 0→1이고 **1에 닿으면 다운**입니다. 그리고 **초당 0.12씩 빠집니다** —
그래서 펀치를 *모아서* 넣어야 합니다.

| | 버스트로 다운까지 | 한 방이 사라지는 시간 |
| --- | --- | --- |
| 잽 | 8.9방 | 0.9초 |
| 스트레이트 | 4.9방 | 1.7초 |
| 훅 | 4.2방 | 2.0초 |
| 어퍼컷 | 3.6방 | 2.3초 |

**약 8초 안에 넣어야** 하고, 흩어서 넣으면 체력바만 갈립니다. 이게 복싱에서
"펀치를 이어서 넣는다"는 게 실제로 의미하는 것이고, 게임의 핵심 기술이 됩니다.

#### 맞으면 무너집니다 (`HurtFactor`)

체력 **절반 아래**부터 지친 선수가 실제로 무너지는 방식대로 무너집니다. 데미지
보정이 아니라 **같은 가드·풋워크 수치가 나빠지는 것**입니다.

- **가드가 안 올라갑니다** — 관통률 ×2.2, 가드 게이지 회복 ×0.45
- **발이 느려집니다** — 이동 ×0.72
- **펀치가 늦습니다** — 선딜·타격·후딜 전부 ×1.35 (약해지는 게 아니라 늦는 겁니다)
- **턱이 먼저 갑니다** — 트라우마 축적 ×1.8 → 몰린 선수는 마무리가 됩니다

다운하면 트라우마가 0이 아니라 **0.35로** 리셋됩니다. 일어나도 종이 울리고 있으니
두 번째 다운이 더 쉽게 옵니다.

### 펀치 조준 — 왼손이 허공으로 가던 이유

펀치 클립은 **애니메이터가 녹음할 때 향하던 방향**으로 날아갑니다. 당신 앞에 선
상대 쪽이 아닙니다. 그래서 왼손이 상대 얼굴이 아니라 왼쪽 허공으로 뻗었습니다.

`ArmPose` 가 **클립은 동작을, IK는 주소를** 담당하게 합니다. 손이 상대 쪽으로
조향되는데, **신장의 후반부에서만** 블렌드되기 때문에 클립의 궤적이 살아남습니다
(`Aim Weight` 0.8 — 1.0으로 올리면 모든 펀치가 직선 찌르기가 됩니다).

히트 판정도 **같은 손 본**을 읽으니, 보이는 곳과 맞는 곳이 일치하게 됩니다.

### 앉기 — 무릎이 접힙니다

C를 누르면 **몸 전체가 내려가서** 발이 캔버스를 뚫고 있었습니다. 피벗을 내리면
발까지 같이 내려가니까요.

`CrouchPose`: **발 위치를 기억하고 → 엉덩이를 내리고 → 다리 IK로 발을 제자리로**
되돌립니다. 발목 아래는 아무것도 안 움직입니다. 그게 차이 전부입니다.

(캡슐 모드에는 무릎이 없으니 기존 피벗 방식을 그대로 씁니다 — `PivotCrouch`.)

### 실제 복서 모델 구하기

**Mixamo 캐릭터일 필요 없습니다.** Unity의 Humanoid 리타게팅이 뼈 매핑을 처리하므로,
**Humanoid 아바타가 유효한 모델이면 지금 가진 Mixamo 클립이 그대로 재생됩니다.**
그게 실제 요구조건이고 훨씬 넓습니다.

#### 바로 확인: `The Fighter → Check Boxer Model`

Project 창에서 모델을 선택하고 실행하면 콘솔에 검사 결과가 나옵니다:

- 스킨 메시가 있는지 (= 몸이 있는지 — `@` 파일은 애니메이션뿐)
- Rig가 Humanoid이고 아바타가 유효한지
- **우리 코드가 쓰는 뼈 15개가 전부 매핑됐는지** (팔 = 가드·조준, 다리 = 앉기)
- 크기 (센티미터 단위로 들어오면 경고)

플레이해보고 콘솔 읽고 추측하는 루프를 안 돌아도 됩니다.

### 상대가 줄에 매달린 것처럼 따라오던 이유

예전 컨트롤러는 **선호 거리 하나를 데드밴드 0.30m로 유지**했습니다. 6.2m 링 안에서
그건 **전체 경기가 가용 거리의 5% 안에서** 일어난다는 뜻입니다. 물러나면 즉시,
매번, 같은 속도로 따라옵니다. 쫓기는 게 아니라 끌려다니는 느낌이 나는 이유입니다.

복서는 **언제 들어갈지를 정합니다.** 그래서 설정값이 아니라 **의도**로 바꿨습니다:

| 의도 | 원하는 거리 | 밴드 | 하는 일 |
| --- | --- | --- | --- |
| **Pressure** | 선호 × 0.78 | 0.14 | 안쪽으로 들어가서 머문다 |
| **Hold** | 선호 | **0.42** | 자기 사거리에서 작업 |
| **Reset** | 선호 + 0.7~1.4 | 0.35 | 일부러 빠져서 숨 고르고 움직인다 |
| **Cut** | 선호 + 0.15 | 0.3 | 링을 자른다 |

**넓은 밴드가 핵심입니다** — 그 안에서는 아예 보정하지 않으므로 거리가 실제처럼
흘러다닙니다. 의도는 **1.3~3.4초** 유지됩니다. 더 짧으면 결정이 아니라 떨림으로 보입니다.

선택은 결정 트리가 아니라 **가중치**입니다 — 지치거나 다치면 Reset 쪽으로, 공격적인
스타일이면 Pressure 쪽으로 기울되 같은 상황이 항상 같은 선택을 내놓지는 않습니다.

#### 링 커팅

| 우선순위 | |
| --- | --- |
| 1 | **내가 로프에 몰렸으면** 로프를 따라가지 말고 열린 바닥 쪽으로 돈다 |
| 2 | **상대가 몰렸으면** 상대가 도망칠 공간(= 중앙 방향) 쪽을 먼저 차지한다 |
| 3 | 아니면 평소대로 서클링 |

2번이 **사람을 쫓는 것과 가두는 것의 차이**입니다. 열린 공간에서 하는 커팅은 의미가
없으므로 상대가 중앙에서 충분히 벗어났을 때만 발동합니다 (`CutThreshold`).

### 뒤로 갈 때 점프하던 이유

`HipHeightLock` 이 **액션 가중치로 스케일**됩니다 (펀치·다운). 뒤로 걷는 건 **베이스
레이어뿐**이라 액션 가중치가 0 — **엉덩이 고정이 아예 안 걸립니다.** `Step Backward`
클립 자신의 엉덩이 높이가 그대로 적용돼서, 클립이 블렌드되는 순간 몸이 솟거나 가라앉습니다.

엉덩이를 그냥 고정하면 **스탠스를 살아 있게 만드는 상하 흔들림이 죽습니다.** 그래서
**클립마다 자기 쉬는 높이를 학습**하고, **클립 사이의 차이만** 상쇄합니다:

| | |
| --- | --- |
| 학습 조건 | 그 클립이 베이스 가중치의 **90% 이상**을 혼자 들고 있을 때 |
| 학습 방법 | 느린 평균 — 클립 자신의 흔들림이 상쇄되어 "높이"로 오해되지 않게 |
| 상쇄 대상 | 현재 믹스의 기대 높이 − 아이들의 높이 |
| 보존되는 것 | **각 클립 안의 흔들림 전부** |

블렌드는 이미 두 클립의 평균이라 섞여 있는 동안은 높이를 측정할 수 없습니다. 그래서
한 클립이 거의 전부를 들고 있을 때까지 기다립니다 (`FootworkHipLock`).

### 어퍼컷 팔이 흔들리던 이유

조준 IK가 `PunchTrack` 0.2부터 램프업해서 0.95에 도달하는데, Strike → Recovery 전환에서
`aiming` 이 false가 되면서 **한 프레임에 0.95 → 0** 으로 떨어졌습니다.

느린 펀치에서는 그 스냅이 애니메이션 전체에서 가장 눈에 띕니다. 어퍼컷이 가장 느리니
가장 심했습니다.

이제 **올라갈 때는 펀치를 정확히 따르고**(주먹은 조준한 곳에 도착해야 합니다),
**내려올 때는 감쇠**합니다 (`AimReleaseSpeed` 6). 돌아오는 길에는 아무것도 도착할
필요가 없습니다.

### 발이 안 움직일 때 — 원인이 네 가지입니다

"가끔 스텝을 안 밟는다"는 겉보기로는 구분이 안 되는 네 가지가 있습니다:

| 원인 | 프로브에서 보이는 것 |
| --- | --- |
| 그 방향 클립이 없음 | `clip fit` 로그의 `(no clip)` |
| 가중치가 도달하기 전에 입력이 끝남 | `w` 가 낮음 |
| 대각선이라 한 스텝이 두 클립으로 쪼개짐 | `effort` 는 높은데 `w` 가 절반 |
| 속도가 낮아 스트라이드가 거의 멈춤 | `stride` 가 0.5 근처 |

`P` 패널에 **`feet` 줄**이 추가됐습니다:

```
feet    in 0.82  effort 1.00  stride 1.21x  w 0.94  Boxing Step Forward
```

움직이는데 스텝 가중치가 낮으면 **`MOVING WITHOUT STEPPING`** 이 빨갛게 뜹니다.

그리고 **풋워크 블렌드 속도를 따로 뒀습니다** (`FootworkBlendSpeed` 20, 스탠스는 9).
스텝은 분위기가 아니라 사건이라서, 스탠스 속도로는 짧게 누른 입력이 블렌드되는 데
시간을 다 쓰고 **도달하지 못합니다** — 그게 정확히 "스텝을 안 밟는" 것처럼 보입니다.
`StepDeadzone` 도 0.12 → 0.08, `StepFullSpeed` 0.55 → 0.38 로 내려서 더 일찍 꽉 찹니다.

### 가드가 안 올라가던 이유 — 앉기와 같은 버그

`HandleGuard` 가 `State == Free` 만 허용했습니다. 즉 **Recovery 동안 가드가 올라가지
않습니다** — 펀치를 던진 직후, 정확히 카운터가 날아오는 순간입니다.

| 내가 던진 펀치 | 후딜 | 들어오는 잽 |
| --- | --- | --- |
| 잽 | 0.18초 | 0.20초 — 간신히 |
| 스트레이트 | 0.28초 | **카운터 막기 불가** |
| 훅 | 0.34초 | **카운터 막기 불가** |
| 어퍼컷 | 0.42초 | **카운터 막기 불가** |

**펀치를 던지고 나면 카운터가 구조적으로 막을 수 없었습니다.** 손을 거두는 게 곧
가드를 올리는 것인데, 그걸 못 하게 막고 있었습니다. 이제 Recovery 에서도 올라갑니다
(Windup 은 그대로 — 손이 나가면 나간 겁니다).

`ArmPose.GuardClipAssist` 도 추가했습니다. Guard 클립이 있으면 IK가 완전히 물러나던
걸 **55%는 남기게** 했습니다. 가드가 전적으로 클립 품질에 달려 있으면 안 됩니다.

### 가드가 한 손만 올라가던 이유

```csharp
SolveSide(true,  leftThrowing, ...);
SolveSide(false, !leftThrowing, ...);   // 펀치가 없으면 !false = true
```

펀치가 없을 때 **오른팔이 "던지는 중"으로 판정**돼서 가드 가중치가 0으로 깎였습니다.
그래서 오른손은 절대 올라가지 않았습니다. 이제 양쪽 모두 **펀치가 존재할 것**을
요구합니다.

### 가드는 하나의 자세가 아닙니다

복싱에는 여러 가드가 있고, **어느 가드를 하고 있는지가 무엇을 예상하는지**를 말해줍니다.
이게 방어가 "방어"로 보이게 하는 거의 전부입니다.

| 상황 | 가드 | 왜 |
| --- | --- | --- |
| 직선 펀치 | **High** — 손이 광대뼈, 약간 앞 | 기본 |
| **훅** | **HookCover** — 관자놀이에 바싹, 팔꿈치 올림, **날아오는 쪽 손은 귀 위로** | 하이 가드는 훅에 아무 역할도 못 합니다. 훅은 가드를 *통과*하지 않고 *돌아서* 옵니다 |
| 바디 / 어퍼컷 | **BodyCover** — 팔꿈치를 갈비뼈로 | 머리를 내주는 게 트레이드 |

**들어오는 펀치를 읽어서** 고릅니다 (무작위 아님). 어느 쪽 귀를 덮는지는 **상대가
어느 손으로 던지는지**가 정합니다 — 사우스포면 반대로 뒤집힙니다.

조합 중에 가드가 깜빡이지 않게 **0.35초 홀드**가 걸려 있습니다.

### 데미지 위치 표시 (`B` 키)

체력바 하나는 **얼마나 남았는지**만 말하고 **어디로 갔는지**는 말하지 않습니다. 복싱에선
어디로 갔는지가 이야기의 전부입니다 — 밤새 바디를 두들겨 맞은 선수와 턱을 맞은 선수는
완전히 다른 곤경에 있는데 바는 똑같이 보입니다.

`B` 를 누르면 각 선수의 **머리와 몸통 위에 마커**가 뜹니다:

- **색**: 흰색 → 황색 → 빨강 (누적 데미지)
- **크기**: 데미지와 함께 커집니다 (작은 화면/녹화에서도 읽히게)
- **숫자**: 누적 피해량, `(blk N)` = 가드로 막은 양, 머리엔 `CHIN %`
- 머리 마커는 **히트박스를 따라다닙니다** — 린/크라우치가 실제로 맞는 부위를 움직이는지
  같이 확인됩니다

실제 모델이 붓기와 상처로 보여줄 수 있을 때까지의 대역입니다. `BoxingBootstrap` →
**Damage Map On** 으로 처음부터 켤 수 있습니다.

### 펀치가 빗나가는지 수치로 (`P` → `aim` 줄)

"왼쪽 허공으로 간다"는 문장이고, 이건 거리입니다. 최대 신장 순간에 **글러브와 조준점
사이 거리**를 재서 `aim` 줄에 표시합니다. 접촉에 필요한 건 약 0.23m라서, 그게
"조준됨"과 "지나침"의 경계입니다. 최악값도 따로 들고 있습니다.

`Aim Weight` 를 0.8 → **0.95**, `Aim Start Track` 을 0.3 → **0.2** 로 올렸습니다.
그래도 `MISSING THE TARGET` 이 나오면 수치를 알려주세요 — IK가 아예 안 돌고 있는 건지
조준점이 틀린 건지 구분됩니다.

### 클립 선택 — 슬롯을 쪼개지 않고 조건을 태깅합니다

**이게 UFC·EA 격투 게임이 실제로 하는 방식입니다.** 게임플레이가 *히트 정보*를 만들고,
애니메이션 시스템이 그에 **가장 맞는 클립을 질의**합니다. 상태마다 슬롯이 하나 있는
구조가 아닙니다.

슬롯을 방향별로 쪼개면 **부위 3 × 방향 4 × 강도 2 = 24칸**이 되고, 축을 하나 더
추가하면 다시 두 배가 됩니다. 그래서 `ClipVariant` 에 조건을 붙였습니다:

```
Hit Head
  [0] Clip: Standing React Large From Left    Direction: Left    Force: Heavy
  [1] Clip: Standing React Large From Right   Direction: Right   Force: Heavy
  [2] Clip: Standing React Small From Front   Direction: Front   Force: Light
  [3] Clip: Taking Punch                      Direction: Any     Force: Any
```

**점수로 고릅니다, 걸러내지 않습니다** — 그래서 슬롯이 비지 않고 *degrade* 합니다:

| | |
| --- | --- |
| 방향·강도 둘 다 맞음 | 4점 — 최우선 |
| 방향만 맞음 | 2점 |
| `Any` (와일드카드) | 0점 — 맞는 게 없을 때 쓰입니다 |
| **다른 방향으로 태깅됨** | **실격** — 오른쪽에서 온 펀치에 오른쪽으로 꺾이는 건 반응이 없는 것보다 나쁩니다 |

동점이면 무작위 — 다양성은 거기서 나옵니다. **클립 하나만 넣으면 `Any` 로 모든 상황에
쓰입니다.** 지금처럼요.

#### 방향은 접촉점에서 계산합니다 (던진 손이 아니라)

상대의 **왼쪽 훅은 내 오른쪽에** 맞습니다. 그래서 펀치 종류를 묻지 않고 접촉점을
내 기준 좌표로 변환해서 판정합니다:

| 접촉 | 판정 |
| --- | --- |
| 스트레이트 (정면) | `Front` |
| 왼손 훅 → 내 오른쪽 | `Right` |
| 오른손 훅 → 내 왼쪽 | `Left` |
| **넓게 들어온 스트레이트** | `Right` — **의도된 결과입니다.** 넓은 스트레이트는 옆으로 밀려야 하고, 정면으로 받은 훅은 안 밀려야 합니다 |

강도는 데미지 14 이상이면 `Heavy`. 잽은 대부분 Light, 파워펀치는 대부분 Heavy로 갈립니다.

#### 조건이 걸린 슬롯

| 슬롯 | 쓰는 조건 |
| --- | --- |
| `Hit Head` / `Hit Body` | 방향 + 강도 |
| `Slip` | 방향 (Q/E 린 방향) |
| `Guard Hook` | 방향 (훅이 오는 쪽 귀) — **매 프레임 선택**, 훅 중간에 안 바뀝니다 |
| `Down` | 방향 (쓰러뜨린 펀치) |
| 펀치 4종 | 무작위 (변형) |

### 태깅은 파일 이름에서 읽습니다 — 손으로 안 넣어도 됩니다

Mixamo가 이미 이름에 다 적어뒀습니다. `Standing React Large From Left` 안에 방향과
강도가 들어 있는데, 그걸 클립마다 드롭다운 두 개에 다시 입력하라고 하면 수십 개에서
시스템이 안 쓰이게 됩니다.

| 이름에 있으면 | 읽는 값 |
| --- | --- |
| `left` / `right` / `front`·`forward` / `back`·`behind` | `Direction` |
| `heavy` **또는 `large`** | `Force = Heavy` |
| `light` **또는 `small`** | `Force = Light` |

Mixamo의 단어(Large/Small)와 직접 붙이신 단어(Heavy/Light)를 **둘 다** 읽습니다.
인스펙터에서 명시적으로 지정하면 **그쪽이 항상 이깁니다** — 이름 읽기는 빈칸만 채웁니다.

> `X Bot@Standing React Large From Left Heavy` → `Direction: Left`, `Force: Heavy`
> 자동입니다. 넣기만 하세요.

### 훅과 어퍼는 양손 펀치가 됐습니다 (`Left hook` / `Right hook`)

`Hook`의 손이 **Lead 고정**이었습니다. 오소독스면 항상 왼손. 그래서 `Right hook`을
슬롯에 넣으면 **절반은 안 쓰는 팔이 휘둘러집니다** — 어퍼에서 보신 그 증상과 같은
원인입니다. 복싱에 좌훅과 우훅이 둘 다 있으니 코드가 틀린 거였습니다.

| 이름에 있으면 | 읽는 값 |
| --- | --- |
| `left` / `right` | `Side` (새로 추가) |

`Side`는 다른 조건과 달리 **점수가 아니라 실격**입니다. 방향이 틀린 피격 클립은
아쉬울 뿐이지만, 팔이 틀린 펀치 클립은 **판정·조준·가드 해제가 전부 다른 팔을 보고
있기 때문에** 대체재가 될 수 없습니다.

- 콤보로 이어지면 **반대 손**으로 나갑니다 — 잽 → 우훅, 원투 → 좌훅. 콤보 캔슬 규칙이
  "다른 손만 끊을 수 있다"였으니 그대로 흐릅니다.
- 단발로 던지면 기본 손(`Hand`)입니다.
- **한쪽 클립만 있으면 그쪽 손으로만 나갑니다.** 지금 어퍼가 왼손 하나뿐이니 어퍼는
  전부 좌어퍼입니다. 우어퍼 클립을 넣으면 그때부터 번갈아 나갑니다. 없는 팔로 던져서
  빈 팔이 휘두르는 것보다 이게 낫습니다.
- 같이 고친 것: `TransferPower`가 `punch.Hand`(정의상 기본 손)를 읽고 있어서 **우훅이
  좌훅 체중 배분(0.18)으로 계산되고 있었습니다.** 실제로 던진 손(`ActiveHand`)을 읽게
  바꿨습니다 — 우훅이 제 힘(0.6)을 찾았습니다.
- 봇도 같이: 훅은 측면에서 오니 린(기울이기)으로 피하면 궤적 안으로 머리를 넣는
  셈입니다. 훅엔 가드 74% / 린 4%, 어퍼엔 가드 30% / 린 34%로 갈렸습니다.

`P`의 clip fit 로그에 `[방향/강도/손]`이 찍히고, 한쪽이 비면
`either hand: left yes right NO`로 알려줍니다.

### 피격 클립은 자기 시계로 돕니다

리코일(`RecoilSeconds` 0.20초)은 **절차적 머리 꺾임**용으로 맞춰진 값입니다. Mixamo
react 클립은 1초가 훌쩍 넘습니다. 그 시계로 돌리면:

| | |
| --- | --- |
| 1.5초 클립, Window `0~0.7` = 1.05초 | |
| 리코일 시계 0.17초에 재생 | **6.2배속** — 반응이 아니라 경련 |
| 클립용 시계 0.45초에 재생 | 2.3배속 — 읽힙니다 |

그래서 `HitReactionSeconds` (기본 0.45초, Heavy는 ×1.35)를 따로 뒀습니다. 리코일은
**"맞았다"와 "어느 부위"만** 알려주고, 클립은 자기 속도로 돕니다.

그리고 둘이 **하나의 반응**이 되도록, 피격 클립이 있으면 절차적 리코일이 0.4로
줄어듭니다 (`Procedural Recoil With Clips`). 클립이 반응을 맡고, 절차적인 건 첫 프레임을
날카롭게 하는 역할만 남습니다.

#### 이름 읽기는 **직접 붙인 단어가 이깁니다**

Mixamo는 `Standing React **Large** From Left` 로 내보냅니다. Large 변형만 받아서
뒤에 `Light` / `Heavy` 를 붙이면 **모든 파일에 "Large"가 들어 있어서**, `large` 를 먼저
검사하면 Light 클립까지 전부 Heavy로 읽힙니다. 실제로 그렇게 됐었습니다.

그래서 검사 순서가 **`heavy` → `light` → `large` → `small`** 입니다. 일부러 타이핑한
단어가 다운로드에 딸려온 단어를 이깁니다.

#### 보고서는 양쪽을 다 잡습니다

**너무 느린 것도 틀린 겁니다.** 빠른 건 뭉개져서 바로 보이지만, 슬로모션은 반응처럼
보이기 때문에 놓치기 쉽고 — **무게가 없게** 느껴집니다.

| | |
| --- | --- |
| `1.8x` 초과 | `TOO FAST` |
| `0.7x` 미만 | `TOO SLOW` |
| 모든 줄 | `1x would be 0.00-0.XX` — 그대로 넣으면 됩니다 |

Heavy 태깅된 클립은 **더 긴 시간(×1.35)** 을 받으므로 그 기준으로 측정합니다.

#### Window 는 **비워두면 자동으로 맞춰집니다**

숫자를 13개 타이핑하라고 드리는 건 잘못된 해결이었습니다. 코드가 정답을 이미
계산해서 로그에 찍고 있었으니, **적용도 코드가 합니다.**

`Window` 를 **`0, 0` 으로 비워두면** 그 액션이 가진 시간 안에서 **생속도(1배속)로
재생되는 구간**이 자동으로 계산됩니다. 로그에 `(auto)` 로 표시됩니다.

| | 전 | 후 |
| --- | --- | --- |
| `0,0` 의 의미 | 클립 전체 → **2~5배속 뭉개짐** | **1배속으로 자동 맞춤** |
| 직접 입력 | 필수 | 클립의 쓸 부분이 앞이 아닐 때만 |

Heavy 태깅된 클립은 **더 긴 시간(×1.35)** 을 받으므로 그 기준으로 맞춰집니다 — 같은
`0,0` 인데 Heavy와 Light가 다른 구간을 받습니다.

루프(아이들·가드·스텝)는 맞출 대상 길이가 없으니 그대로 전체를 씁니다.

> 직접 입력이 필요한 유일한 경우: **쓸 부분이 클립 앞쪽이 아닐 때.** `Body Jab Cross`
> 는 왼잽 → 오른크로스라서 Jab 에 `0~0.5`, Straight 에 `0.45~1` 로 나눠 씁니다.

> ⚠️ **Window Y = 0.7은 아마 깁니다.** Play 하면 콘솔 `clip fit` 로그가 이제 피격·회피
> 슬롯까지 몇 배속인지 알려주고, `TOO LONG` 이면 쓸 구간을 제안합니다. react 클립은
> **앞부분(꺾이는 순간)만** 쓰는 게 보통이라 `0 ~ 0.3` 근처가 될 겁니다. 로그 숫자를
> 그대로 넣으시면 됩니다.

### 지금 필요한 Mixamo 클립 — 슬롯은 만들어뒀습니다

찾아서 넣어주시면 상황에 맞게 나갑니다. 비워두면 지금처럼 IK/절차적 반응이 대신합니다.

Mixamo에 **`Standing React` 계열**이 있습니다 — 방향별로 나뉘어 있어서 지금 만든
조건 선택에 그대로 들어맞습니다. **여기가 가장 먼저 받을 것입니다:**

| 받을 것 | 슬롯 | 태깅 |

| `Standing React Large From Left` | `Hit Head` | Direction **Left**, Force **Heavy** |

차이가 가장 크게 나는 부분입니다.

**나머지 (검색어 기준 — Mixamo 이름은 바뀔 수 있습니다):**

| 검색어 | 슬롯 | 태깅 | 왜 |

귀**를 덮는 클립이 자동으로 나갑니다. 하나만 넣고 `Any` 로 두면 양쪽 다 그걸 씁니다.

머리 꺾임이 **하나의 반응**이 되고, 각자 따로 돌지 않습니다.

> **어퍼컷 동작이 너무 큰 문제**: 클립 문제입니다. Play 하면 콘솔의 `clip fit` 로그가
> 몇 배속으로 재생되는지 알려주고, `TOO LONG` 이면 쓸 구간을 제안합니다. 그 숫자를
> `Window` 에 넣으면 됩니다. 어퍼컷은 `0 ~ 0.35` 정도부터 시도해보세요.

### 앉기는 기술입니다 — 잽을 흘리고 바디로

말씀하신 "잽 회피 → 바로 앉아서 바디샷"이 게임의 **첫 번째 진짜 기술**이라서,
숫자가 그걸 할 만하게 만들어야 합니다.

| | |
| --- | --- |
| **턱이 글러브 뒤로 들어갑니다** | 풀 크라우치 + 가드면 머리 관통률 **−45%** |
| **대신 갈비뼈가 열립니다** | 머리만 보호됩니다. 그게 트레이드입니다 |
| **바디샷이 빨라집니다** | 낮은 베이스에서 나가는 짧은 펀치, **−22% 시간** |
| **다리가 실립니다** | 바디 데미지 **×1.2** |

앉은 채로 위를 조준해도 빨라지지 않습니다 — **숙이고 + 아래로 조준**해야 합니다.

### 봇 — 반사와 계획을 분리했습니다

**가장 큰 문제**: AI가 `0.22초`마다 한 번만 생각하는데, 펀치는 **0.19초**에 도착합니다.
즉 **반응이 구조적으로 불가능**했습니다. 가드가 들어오는 펀치에 대한 반응이 아니라
그냥 타이머였습니다.

복서의 손과 복서의 계획은 같은 게 아니라서, 둘로 갈랐습니다:

**반사 — 매 프레임.** 펀치가 시작된 프레임에 봅니다. 그리고 스킬에 따른 지연 후 대응:

| 스킬 | 반응 시간 | 여유 | 시도율 | 결과 |
| --- | --- | --- | --- | --- |
| 0.2 | 0.222초 | −0.030 | 56% | **못 막음** |
| 0.4 | 0.184초 | +0.008 | 66% | 막음 |
| 0.6 | 0.146초 | +0.046 | 77% | 막음 + **퍼펙트 블록 → 카운터** |
| 1.0 | 0.070초 | +0.122 | 98% | 막음 + 카운터 |

퍼펙트 블록 창이 0.18초라서, **잘하는 선수는 막기만 하는 게 아니라 일찍 막고
카운터를 칩니다.** 약한 선수는 그냥 손이 안 올라갑니다 — 가드를 나쁘게 만드는 것보다
정직합니다.

**가드 규율** — 사거리 안에서는 **기본적으로 손이 올라가 있습니다.** 이게 감당 가능한
이유는 공짜가 아니기 때문입니다: 스태미나를 먹고 **바디로 샙니다**. 그래서 플레이어의
답이 "아래로 가라"가 되고, 위에 쓴 앉기 기술과 정확히 맞물립니다. 벽이 아니라 문제입니다.

#### 심리 요소

| | 언제 | 왜 |
| --- | --- | --- |
| **페인트** | 상대가 **반응을 보이는** 선수일 때만 | 윈드업만 던지고 아무것도 안 나옵니다. 가드를 끌어내고 진짜 펀치는 가드가 떠난 곳으로. 반응 없는 상대에겐 확률이 0에 가까워집니다 |
| **베이팅** | 상대가 **압박해 오는** 선수일 때만 | 일부러 손을 내리고 자리를 지킵니다. 카운터는 이미 준비돼 있습니다 |
| **리듬** | 항상 | 연타와 멈춤. 고정 비트는 선택이 아무리 좋아도 **세 번의 교환 안에 읽힙니다** |
| **패턴 응징** | 원투를 2번 이상 봤을 때 | 당신의 잽 다음에 뭐가 오는지 배우고 **미리 덮습니다** |
| **빈 곳 조준** | 스킬에 비례 | 당신이 위를 막아왔으면 아래로 갑니다. 플레이어가 배울 교훈의 반대 방향 |

`OpponentRead` 가 전부 **지수 이동평균**입니다 — 4라운드에 바디로 전환하면 5라운드에
바디 펀처로 읽힙니다. 첫 종의 당신으로 평균되지 않습니다.

> 주사위를 굴리는 봇은 매번 같은 경기를 하고 플레이어는 아무것도 배우지 못합니다.
> **알아채는** 봇은 플레이어가 뭔가 바꾼 것에 보상을 줍니다 — 격투 게임을 계속
> 플레이할 유일한 이유입니다.

### 판정 볼륨 — "닿아야 맞는다"

히트박스는 **캐릭터의 실루엣**입니다. 넉넉한 버블이 아닙니다.

전에는 머리가 반지름 0.20m (지름 40cm짜리 머리), 몸통이 0.27m (지름 54cm)였고
글러브 판정 반경도 0.17~0.20m였습니다. 합치면 **글러브 표면이 피부에서 9cm 떨어져
있어도 타격 판정**이 났습니다 — 허공을 치는데 둔탁한 소리가 나던 원인입니다.

| | 전 | 현재 | 실제 신체 |
| --- | --- | --- | --- |
| 머리 반경 | 0.20m | **0.13m** | ~0.115m |
| 몸통 반경 | 0.27m | **0.20m** | ~0.185m |
| 몸통 범위 | y 0.53~1.47 (무릎~턱) | **y 0.90~1.46** (벨트~명치) | |
| 글러브 판정 | 0.17~0.20m | **0.095~0.11m** | 10oz 글러브 ≈ 0.10m |

**판정은 점이 아니라 궤적을 훑습니다** (`OverlapCapsule`). 이유가 두 개이고, 히트박스가
작아진 지금은 둘 다 실제로 걸립니다:

1. 스트라이크 한 프레임에 글러브가 머리 상당 부분을 **지나칩니다** — 점 판정은 프레임
   운에 따라 헛손질이 됩니다
2. 근거리에서는 글러브가 머리를 **통과해 뒤로 빠져나갑니다**. 0.62m(최소 간격)에서
   스트레이트 완전 신장 시 글러브-머리 거리가 0.268m로, 필요한 0.230m를 넘어갑니다 —
   점 판정이면 "분명 닿았는데 안 맞는" 바로 그 상황입니다

**거리와 판정은 같은 숫자를 읽습니다.** `EffectiveRange = 펀치 사거리 + 글러브 반경 +
머리 반경 − RangeBite`. 따로 튜닝하면 선수가 허공을 긁거나 서로 몸을 겹칩니다.

**스텝인** — 사거리 밖(최대 `StepInReach` 0.45m)에서 던진 펀치는 **파고들면서** 나갑니다
(최대 `StepInMax` 0.30m). 복서는 펀치에 몸을 실어 들어가고, 이게 없으면 타이밍이 어긋난
입력이 "무시된 것"처럼 느껴집니다. 링을 가로지르는 돌진은 안 됩니다.

> 💡 **히트박스를 눈으로 보려면**: Play 중에 **Scene 탭**으로 넘어가면 `Hurtbox` 기즈모가
> 보입니다 (머리 = 주황, 몸통 = 파랑). 모델이 그 안에 어떻게 들어가 있는지는 숫자로는
> 확인할 수 없고 봐야 압니다.

### 콤보 규칙 — 이번에 들어간 가장 큰 변화

전에는 한 펀치가 **완전히 끝나야** 다음 펀치가 나갔습니다. 그래서 원투가 안 되고
단발만 나갔습니다. 이제:

- 후딜의 **55%** 지점부터 다음 펀치로 **캔슬** 가능 (`ComboCancelFraction`)
- 단, **반대 손만** 가능 — 같은 글러브로 연사가 안 됩니다
- 캔슬하면 스태미나를 **1.35배** 더 씁니다

그래서 **잽(앞손) → 스트레이트(뒷손)** 가 자연스럽게 흐르고, 잽 연타는 막힙니다.
이 규칙 하나가 "펀치를 던지는 것"과 "복싱"의 차이를 만듭니다.

### 튜닝 표 — 느낌이 안 맞을 때 만질 곳

**Play 모드에서 실시간으로 바꿀 수 있는 것** (Hierarchy에서 선수 오브젝트 선택
→ `Fighter Rig` 컴포넌트):

| 증상 | 노브 |
| --- | --- |
| 맞는 반응이 약함 / 과함 | `RecoilDamageReference` (낮추면 강해짐), `RecoilSeconds` |
| 펀치에 몸이 안 실림 | `PunchLunge`, `PunchTorsoYaw`, `PunchLean` |
| 다운 포즈가 어색함 | `DownPosition`, `DownRotation`, `DownFallSeconds` |
| 글러브가 느리게 따라옴 | `RestResponsiveness` |

**코드 상수** (`CombatTuning.cs` / `FighterStats.cs`):

| 증상 | 노브 |
| --- | --- |
| 타격이 끈적함 / 너무 가벼움 | `HitStopClean`, `HitStopTimeScale` |
| 콤보가 느림 / 너무 빠름 | `ComboCancelFraction` (낮추면 빨라짐) |
| 펀치가 느림 | `FighterStats.PunchSpeedScale`, 또는 `PunchLibrary`의 각 펀치 `WindupTime`/`StrikeTime` |
| 후딜이 길어 답답함 | `FighterStats.RecoveryScale` |
| 카메라가 너무 흔들림 | `CameraShakeClean`, `CameraShakeTaken` |
| 맞을 때 화면이 너무 붉음 | `FightHud.DrawDamageFlash`의 `0.42f` |
| 허공인데 맞는 소리가 남 | `HeadHurtboxRadius`, `BodyHurtboxRadius`, 각 펀치 `HitRadius` 줄이기 |
| 분명 닿았는데 안 맞음 | 위 값들 올리기, 또는 `PunchHitTrackThreshold` 낮추기 |
| 펀치가 허공을 가름 (거리가 멀어서) | `StepInReach` 올리기 — 더 멀리서도 파고듭니다 |
| 펀치 한 방에 너무 많이 전진함 | `StepInMax` 줄이기 |

**카메라 / 애니메이션** (Hierarchy에서 `FIGHT CAMERA` 또는 선수 → `Fighter Animation`):

| 증상 | 노브 |
| --- | --- |
| 내 캐릭터 뒷모습이 상대를 가림 | `Fight Camera` → `Orbit Min` 올리기 (22 → 30) |
| 상대가 너무 작게 보임 | `Opponent Bias` 올리기, `Far Distance` 줄이기 |
| 카메라가 너무 높음 / 낮음 | `Height`, `Look Height` |
| 펀치마다 캐릭터가 튐 | `Fighter Animation` → `Hip Height Lock` (1 = 완전 고정) |
| 어퍼컷에서 몸이 안 솟음 | `Hip Height Lock` 낮추기 (0.6~0.7) |
| 스텝 다리가 몸보다 빠름 / 느림 | 해당 스텝 클립의 `Speed` |
| 아이들이 뻣뻣함 | 아이들 클립의 `Speed`, 또는 `Window`로 앞부분 잘라내기 |
| 가드가 닭날개처럼 옆으로 벌어짐 | `Guard Pose` → `Elbow Hint` (y를 더 음수로) |

> **정직한 메모**: 타격감은 제가 직접 느껴볼 수 없는 유일한 영역입니다. 위 수치는
> 복싱 타이밍과 게임 관례에서 뽑은 **출발점**이고, 정답은 직접 쳐보신 감각입니다.
> "어퍼컷이 가벼워요" 같은 말로 알려주시면 어느 노브인지 짚어드립니다.

### 목표: 파이트 나이트 챔피언 — 뭐가 남았나

솔직하게 짚어두면, **FNC의 타격감은 대부분 애니메이션과 에셋에서 나옵니다.**
전투 로직에서 나오는 게 아닙니다.

| FNC의 구성요소 | 지금 상태 |
| --- | --- |
| 풀바디 모캡 애니메이션 (무게가 실린 스텝·펀치) | ❌ **없음. 이게 가장 큰 격차** |
| 어떤 자세에서든 펀치로 블렌딩되는 전환 | ❌ 없음 (Mecanim 필요) |
| 물리 기반 피격 반응 (래그돌 블렌딩) | 🟡 절차적 반응만 (`PlayHitReaction`) |
| 아날로그 스틱 궤적으로 펀치 지정 | 🟡 터치 제스처로 같은 발상 구현 |
| 가까운 카메라·DOF·땀·변형 셰이더 | ❌ 없음 (렌더 파이프라인 작업) |
| 사운드 디자인 | ❌ 절차 생성 땜질 |
| 타이밍·사거리·스태미나·카운터·채점 로직 | ✅ **이미 있음** |

즉 **전투 로직은 그 수준을 받칠 준비가 돼 있고, 몸이 없습니다.** 그래서 다음
단계는 타격감 수치를 더 만지는 게 아니라 **캐릭터**입니다. 지금 캡슐로 모션을
평가하는 건 불가능하다는 판단이 맞습니다.

### 실제 캐릭터 넣기 — 현재 상태와 남은 작업

애니메이션 레이어(`FighterAnimation.cs`)는 작성되어 있습니다. **Animator Controller를
손으로 짤 필요가 없습니다** — 씬의 `BoxingBootstrap` 오브젝트에 클립 슬롯이 있고,
거기에 드래그하면 끝입니다.

설계상 세 가지를 보장합니다:

- **코드가 타이밍의 주인입니다.** 모든 클립의 재생 시간을 매 프레임 직접 지정합니다
  (펀치는 `Fighter.PunchProgress`, 자세·풋워크는 누적 루프 시계). Mixamo 클립 길이는
  우리 선딜/타격/후딜과 무관하므로, 클립이 타이밍을 정하면 사거리·카운터 창·채점
  가중치가 전부 틀어집니다. 이 방식이면 클립의 Loop Time이나 길이를 건드릴 필요도
  없습니다
- **루트 모션은 끕니다** (`applyRootMotion = false`). 위치는 `FighterMotor`가
  움직이므로, Mixamo의 **In Place 체크를 깜빡해도 문제없습니다**
- **실패해도 안전합니다.** 슬롯이 비었거나 모델이 Humanoid가 아니면 이 레이어는
  아무것도 하지 않고 기존 절차적 캡슐 리그로 돌아갑니다

#### 1. 슬롯 구성

**모든 슬롯이 같은 구조입니다.** 슬롯 하나에 클립을 몇 개든 넣을 수 있고, 각 클립마다
`Window`와 `Speed`가 붙습니다.

| 묶음 | 슬롯 | 여러 개 넣으면 |
| --- | --- | --- |
| 스탠스 | `Idle`, `Guard` | 경기 시작 때 **하나를 뽑아 끝까지** 씁니다. 선수마다 다른 자세로 서게 됩니다 |
| 발놀림 | `Step Forward`, `Step Back`, `Step Left`, `Step Right` | 위와 같음 |
| 펀치 | `Jab`, `Straight`, `Hook`, `Uppercut` | **펀치를 던질 때마다 랜덤**으로 하나 |
| 반응 | `Slip`, `Down` | 발동할 때마다 랜덤으로 하나 |

`Idle`만은 비우면 안 됩니다 — 가중치가 0인 Humanoid는 T-pose로 튑니다.

**`Window` (시작·끝, 0~1)** — 클립의 **어느 구간**을 쓸지. **둘 다 0이면 클립 전체**를
씁니다. 경기 타이밍은 바뀌지 않고 보이는 프레임만 바뀝니다.

- 모션이 급하게 보이면 끝값을 줄이세요
- 루프 클립이 제자리 준비동작으로 시작하면 앞부분을 잘라내세요
- 콤보 클립을 쪼개 쓸 수 있습니다. `Body Jab Cross`는 왼잽 → 오른크로스라서
  **Jab에 `0 ~ 0.5`, Straight에 `0.45 ~ 1`** 로 같은 클립을 두 번 쓰면 됩니다

**`Speed`** — 루프(스탠스·발놀림) 전용 재생 속도. 펀치는 타이밍을 코드가 쥐고 있어서
`Speed`를 보지 않습니다.

- 스텝 다리가 몸보다 느리게 끌리면 올리고, 다리만 허둥대면 내리세요
- 아이들이 뻣뻣하면 0.8 정도로 내려보세요

**발놀림은 네 방향을 크기 비율로 섞습니다.** 움직임이 상대 기준(앞뒤 = 거리, 좌우 =
서클링)이라 두 축이 클립 하나에 바로 대응되고, 대각선으로 움직이면 전진과 사이드
스텝이 **동시에** 재생됩니다 — 큰 쪽 하나로 스냅되지 않습니다.

> 사우스포 세트는 "**어느 쪽으로 가 보이는지**" 기준으로 넣으세요. 오소독스를
> 미러링해서 만들면 좌우 스텝이 뒤집히므로, 미러한 *Step Left* 클립은 사우스포의
> `Step Right` 칸에 들어갑니다.

**`Guard` 슬롯은 비워도 됩니다.** 비어 있으면 `GuardPose`가 IK로 글러브를 얼굴까지
올립니다. 클립을 넣으면 IK는 **자동으로 물러납니다** — 애니메이션 가드와 IK 가드가
서로 싸우면 둘 다 망가지기 때문입니다 (`Guard Pose` → `Defer To Guard Clip`).

**점프처럼 튀는 문제 (`Hip Height Lock`)** — Mixamo 클립마다 엉덩이 높이 기준이 달라서,
아이들에서 펀치로 블렌드하면 몸 전체가 위로 솟습니다. 그래서 엉덩이를 **스탠스가
서 있는 높이에 고정**하는데, **액션이 재생되는 동안만** 그 액션의 가중치만큼
적용합니다. 항상 고정하면 아이들과 스텝 사이클의 상하 흔들림까지 죽어버리고, 그
흔들림이 자세를 살아 있게 만드는 거의 전부입니다.

- 어퍼컷에서 몸이 솟는 느낌을 살리고 싶으면 0.6~0.7로 내리세요
- 근본 해결은 클립별 임포트 설정 (Root Transform Position (Y) → Bake Into Pose,
  Based Upon Feet)이고, 이건 체크 한 번으로 때우는 버전입니다

#### 2. 아직 없으면 받을 것

| 받을 것 | Mixamo 위치 | 왜 |
| --- | --- | --- |
| **`X Bot.fbx` (캐릭터 본체)** | 상단 **Characters** 탭 → `X Bot` | ⚠️ **필수.** `X Bot@동작` 파일들은 전부 애니메이션만이라 몸이 없습니다 |
| `uppercut` | Animations | 펀치 4종 중 가장 자주 빠짐 |
| `taking punch`, `knocked out` | Animations | 피격·다운 (없으면 절차적 반응이 대신함) |

캐릭터는 Format **FBX for Unity**, Pose **T-pose**. 애니메이션은 **Without Skin**.

내용을 모르는 클립(`X Bot@Boxing`, `Boxing (1)` 등)은 Project 창에서 클릭하면
인스펙터 **아래쪽 미리보기 창**에서 재생해볼 수 있습니다.

#### 3. Unity에서 연결하기

1. 씬을 열고 Hierarchy에서 **`BoxingBootstrap`** 선택
2. **Boxer Model** 칸에 `X Bot.fbx`를 드래그
3. **Orthodox Clips** 를 펼칩니다. 모든 슬롯이 배열이라 슬롯마다 **+** 를 눌러
   칸을 만들고, 그 안의 `Clip`에 클립을 넣습니다 (`Window`는 0,0 그대로 두면 전체)
   - ⚠️ **FBX 자체가 아니라 그 안의 클립**을 넣어야 합니다. Project 창에서 FBX 왼쪽
     화살표(▶)를 펼치면 나오는 항목 중 **삼각형 모양 아이콘**이 AnimationClip입니다
   - 같은 슬롯에 **+** 를 더 눌러 다른 모션을 넣으면 변형이 됩니다
4. **Southpaw Clips** 는 비워둬도 됩니다 — `Idle`이 비어 있으면 아무도 사우스포를
   배정받지 않습니다
5. **Play** — 모델이 캡슐을 대체하고, 캡슐은 숨겨진 채 폴백으로 남습니다

모델 키가 안 맞으면 `Model Scale`, 바라보는 방향이 틀어졌으면 `Model Yaw Offset`로
맞추세요. 펀치마다 캐릭터가 점프하듯 튀면 `Hip Height Lock`(기본 1)을 확인하세요.

#### 4. 남는 한계

- **1인칭은 모델과 함께 쓸 수 없습니다.** FP에서는 내 몸을 숨기는데, 모델은 손도 몸의
  일부라 아무것도 안 보입니다. FPS가 쓰는 별도 팔 모델(viewmodel)이 필요한 문제이고,
  브로드캐스트 3인칭이 기본이라 당장은 보류합니다
- 머리 전용 피격 스냅은 모델에서는 빠집니다. 몸 전체 반동·기울기·다운 포즈는
  `BodyPivot`을 통해 애니메이션 위에 그대로 얹힙니다

```
│   └── HitEvent.cs             #   판정된 펀치 한 건
├── Fight/
│   ├── Fighter.cs              #   체력·스태미나·가드게이지, 펀치 상태머신, 피격 처리, 다운/KO
│   ├── FighterMotor.cs         #   CharacterController 풋워크 + 상대 자동 바라보기 + 링 경계
│   ├── FighterRig.cs           #   몸 전체 절차 애니메이션: 글러브·스탠스 반전·펀치 궤적
│   │                           #   + 몸 커밋·피격 반응·다운 포즈·스텝 셔플
│   ├── FighterAnimation.cs     #   실제 Humanoid 클립 재생 (Playables, 컨트롤러 불필요)
│   ├── Hurtbox.cs              #   머리 / 몸통 피격 볼륨
│   ├── TouchBrain.cs           #   터치 제스처 → FighterIntent (모바일 기본)
│   ├── PlayerBrain.cs          #   키보드·마우스 → FighterIntent (PC 테스트용)
│   ├── AIBrain.cs              #   스타일 기반 판단 + 경기 중 동적 스타일 전환
│   ├── FightCamera.cs          #   브로드캐스트 카메라(기본) + 1인칭, 흔들림/FOV 킥/푸시인
│   ├── ImpactFeedback.cs       #   히트스톱 + 카메라 흔들림 + 절차적 타격음(에셋 0개)
│   ├── Scorecard.cs            #   라운드별 집계 + 심판 3명 10점 머스트 채점 + 판정
│   ├── FightDirector.cs        #   라운드 상태머신(개시→라운드→휴식→판정), 이벤트 배선
│   └── FightHud.cs             #   IMGUI 디버그 HUD (임시, H키로 Full/Minimal/Off)
├── Bootstrap/BoxingBootstrap.cs    # 링·조명·양 선수·카메라·HUD를 코드로 구성
└── Editor/PrototypeSceneBuilder.cs # "The Fighter" 메뉴 → 씬 자동 생성
```

`Fighter`는 **무엇을 할지 결정하지 않습니다.** `IFighterBrain`이 매 프레임
`FighterIntent`(이동/가드/회피/펀치/조준)를 넘기고, `Fighter`는 그걸 실행만
합니다. 그래서 플레이어와 AI가 **완전히 같은 전투 코드**를 지납니다.

## 10. 개발 순서 — 모바일 출시까지

목표는 모바일 출시입니다. 순서의 핵심은 **터치 복싱이 재미있는지를 가장 먼저,
가장 싸게 확인하는 것**입니다. 그게 아니면 커리어·UI·아트가 전부 버려집니다.

- [x] **0단계 — 전투 프로토타입**
      이동/서클링, 펀치 4종, 양손 글러브 + 스탠스 반전, 가드 + 가드 게이지,
      회피, 머리/몸통 히트박스, 카운터 2종, 스태미나, 3-다운제 KO,
      스타일 6종 + AI 동적 전환, 히트스톱·흔들림·타격음
- [x] **1단계 — 터치 컨트롤 + 브로드캐스트 카메라 + 스탯 밸런스**

      스피드/스킬 타이밍 분리, 가로 고정 + 60fps
- [x] **2단계 — 경기 규칙: 라운드와 판정**
      90초 라운드 + 12초 코너, 단계별 경기 거리(3~8R), 10점 머스트 3심 채점,
      만장일치/스플릿/다수/무승부 판정, 코너 회복(후반에 약해짐),

## 11. 알려진 제약

- **터치 컨트롤은 아직 실기기에서 검증되지 않았습니다.** 에디터 마우스
  시뮬레이션으로만 확인 가능한 상태이고, 1.5단계가 바로 그 검증입니다.
- **1인칭 글러브 위치와 엄지가 충돌할 가능성**이 남아 있습니다. PC에서는
  글러브를 화면 아래 가장자리로 내려 시야를 확보했는데(4절), 폰에서는 바로
  그 자리가 엄지 밑입니다. 실기기에서 확인하고 1인칭/3인칭을 결정해야 합니다.
- **Unity 에디터에서 컴파일 검증을 하지 못한 코드가 포함됩니다.**
  작성 환경에 Unity도 .NET 컴파일러도 없어서 구조 검사(괄호 균형, 타입 멤버
  교차 확인)까지만 했습니다. 에러가 나면 알려주세요.
- `Packages/`와 대부분의 `ProjectSettings/`는 저장소에 없습니다.
  Unity가 처음 열 때 기본값으로 생성합니다. **출시 전에는 커밋해야 합니다**(8절).
- HUD는 전부 영문입니다. Unity 기본 IMGUI 폰트에 한글 글리프가 없어서
  한글을 쓰면 네모로 깨집니다. 5단계에서 폰트 에셋과 함께 한글화합니다.
- 캐릭터는 캡슐+구 프리미티브입니다(의도적).
- 에디터 터치 시뮬레이션은 손가락이 하나뿐이라 이동과 펀치를 동시에 넣을 수
  없습니다. 제스처 인식 확인용입니다.

## 12. 메뉴와 인터페이스 — 구현 계획

### 가장 중요한 결정: UI보다 루프가 먼저입니다

커리어 루프(**경기 제의 → 수락/거절 → 경기 → 결과 → 성장**)가 재미없으면 그 위에
올린 UI는 전부 버려집니다. 반대로 루프가 재미있으면 못생긴 UI로도 그게 느껴집니다.

그래서 순서는 **데이터 → 흐름 → 화면**입니다. 지금의 IMGUI HUD를 임시로 한 번 더
쓰면서 루프를 먼저 굴려보고, 재미가 확인된 다음에 픽셀을 씁니다.

### 설계 원칙 — 경기 씬은 커리어를 몰라야 합니다

```
FightSetup  ──►  [ 경기 씬 ]  ──►  FightOutcome
 (선수 2명,                        (승패, 방식, 라운드,
  라운드 수,                        스코어카드, 통계)
  무대, 심판)
```

경기 씬이 커리어를 직접 읽으면 경기를 단독으로 테스트할 수 없게 됩니다 — 지금처럼
`BoxingBootstrap`만 눌러서 바로 싸워보는 게 불가능해집니다. 구조체 두 개로 끊어두면
커리어와 전투를 **따로 개발하고 따로 디버그**할 수 있습니다.

### 화면 구성

| 화면 | 역할 | 들어가는 것 |
| --- | --- | --- |
| **홈** | 허브 | 선수 카드(전적·스테이지·자금), 새 제의 알림, 다음 경기 |
| **경기 제의** | 수락/거절 | 제의 2~3개, 상대 카드, 파이트머니, 라운드, 거절 대가 |
| **캐릭터** | 성장 | 스탯 4종, 훈련 배분, 스탠스 선택, 추론된 스타일 표시 |
| **대면** | 경기 직전 | 양쪽 카드 비교, 상대 스타일 상성, 최종 확인 |
| **경기** | 전투 | 새 HUD (아래) |
| **결과** | 피드백 | 판정 방식, 심판 3명 스코어카드, 파이트머니, 스탯 상승 |
| **기록** | 커리어 | 전적 리스트, 타이틀 이력, 통계 |

### 경기 HUD — 화면 점유 목표를 숫자로

> "경기중에 두 선수의 스탯화면이 거의 화면 절반을 잡아먹고 화질도 안좋다"

그래서 목표를 느낌이 아니라 숫자로 박습니다.

- **상단 바 ≤ 화면 높이의 12%** — 체력·스태미나·라운드·시간만
- **액션 중에는 측면 패널 없음** — 스탯 상세는 라운드 사이 코너 화면에서
- **TextMeshPro SDF** — 지금 비트맵 폰트의 화질 문제가 여기서 해결됩니다
- 가드 게이지는 선수 발밑 월드 공간 링으로 — 화면을 안 먹습니다

### 7.1 완료 — 커리어 루프 돌려보기

`BoxingBootstrap` 인스펙터에서 **Career Mode** 를 체크하고 Play 하면 됩니다.
끄면 지금까지처럼 바로 스파링으로 들어가니, 타격감 튜닝은 그대로 하실 수 있습니다.

```
홈 ──► 경기 제의 ──► 계량 ──► 경기 ──► 결과 ──► 홈
 └──► 훈련 / 휴식 ──┘        └──► 전적 기록
```

저장은 `Application.persistentDataPath/career.json` 에 자동으로 됩니다.
(Windows: `%USERPROFILE%\AppData\LocalLow\<회사명>\<프로젝트명>\`)

#### 커리어 설계 — 결정이 결정이 되도록

**모든 제의 묶음에는 같은 3지 선택이 들어갑니다**: 조정 경기 / 동급 / 상위 랭커.
파이트머니가 난이도를 따라 움직이기 때문에 "그냥 더 좋은 제의"는 존재하지 않습니다.
난이도 지수를 2.2승으로 둬서 **상위 랭커가 조정 경기의 1.91배**를 받습니다 — 선형으로
했을 때는 25% 차이밖에 안 나서 아무도 고민하지 않았습니다.

**승격은 위를 이겨야 됩니다.** 조정 경기 승리는 돈만 됩니다. 이게 없으면 안전한 선택이
빠른 선택이기도 해서, 커리어 전체가 걸려 있는 위험 판단이 사라집니다.

| | 승격 |
| --- | --- |
| 상위 랭커 승 | 즉시 +1 |
| 동급 승 | 2승 누적 시 +1 |
| 조정 경기 승 | 자금만 |
| 3연패 | −1 |

**컨디션**은 경기를 거절할 이유입니다. 체력이 아니라 준비 상태이고, 낮으면 그 경기
동안 **스탯이 깎입니다** (최저 72%). 경기는 −18에 받은 데미지만큼 더, 휴식은 +22,
훈련은 −9. 그래서 "훈련을 더 할까, 몸을 만들고 나갈까"가 매주 실제 선택이 됩니다.

#### 시뮬레이션으로 잡은 것 — 상대는 스테이지를 따라가야 합니다

처음에는 상대 레이팅을 **플레이어의 현재 레이팅**에 비례시켰습니다. 400주를
시뮬레이션해보니 동급 경기만 받는 커리어가 **스테이지 3에서 영구히 멈췄습니다.**

원인: 그렇게 하면 훈련해도 상대가 같이 강해져서 동급 경기가 **영원히 반반**입니다.
승격은 패배 전에 2승, 강등은 연패 — 50%에서는 두 확률이 상쇄됩니다. 훈련이 사는 건
화면에 찍히는 숫자뿐인 러버밴딩이었습니다.

그래서 **상대는 스테이지가 정합니다** (`CareerConfig.StageRating`). 플레이어 레이팅은
보지 않습니다. 전략별로 16커리어씩 돌려서 기울기를 잡았습니다:

| 기울기 | 동급 경기 전적 | 경기 수 | 스테이지 10 도달 |
| --- | --- | --- | --- |
| 6.2 | 49-50 (챔피언인데 지는 전적) | 99 | 16/16 |
| **4.6** | **37-31** | **~70** | **16/16** |
| 훈련 안 함 | 65-101 | 166 | **0/16** — 스테이지 3에서 정지 |

**훈련은 모든 기울기에서 필수로 남았습니다.** 훈련하지 않는 커리어는 전략과 무관하게
스테이지 3 근처에서 멈춥니다.
